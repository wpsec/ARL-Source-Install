# 证据标准

输出最终结论时，优先使用这套门槛。

## `verified`

至少满足一个强证据：
- 真实暴露且结构可识别的 API 文档端点
- 在响应或 JS 中发现真实硬编码 secret / credential / token 字面量
- WebSocket 握手成功升级
- JWT `alg=none` 或确认弱签名密钥
- 明确的证据片段能直接证明漏洞存在

## `needs_manual_review`

当路线是对的，但证据还不够闭环时使用：
- 受控变异后出现稳定响应差异
- JS 中出现明显 source -> sink 链路
- token 存在，但可利用性尚未完全证实
- ID 变异后输出变化，但鉴权上下文未知
- 目标被访问控制保护，推测需要登录态才能继续

## `likely_false_positive`

当补充上下文后，原始线索塌陷时使用：
- 只有关键词，没有真实字面量
- 静态 JS/框架构建代码里没有危险 sink
- 只是变量拼接、本地存储、主题配置等逻辑
- 探了多个 API 文档路径都没有真实文档结构
- 只是标题或长度变化，没有语义级证据

## 置信度建议

- `0.85+`：只有在强证据成立时使用
- `0.65-0.84`：有价值但尚未完全闭环
- `<=0.64`：信号弱、噪声大或证据不足

## 不应单独抬高置信度的因素

- URL 看起来很像漏洞入口
- 标题发生变化
- 社区 PoC 文库里存在该产品历史漏洞
- 很短的一段证据片段只命中了关键词
