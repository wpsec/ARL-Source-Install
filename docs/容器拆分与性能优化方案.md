# ARL 容器拆分与性能优化方案

## 1. 背景与问题

基于当前实现，`arl_worker` 容器同时运行 4 组 Celery worker（`arltask / arlheavy / arlweb / arlgithub`），并且 `AI 去噪` 也在 `arlweb` 队列中执行。  
这会带来两个典型问题：

1. 单容器内多进程竞争 CPU/内存，重任务高峰时容易互相抢占。
2. `arlweb` 队列既跑 Web 重阶段（目录扫描、nuclei、afrog、截图等），又跑 AI 去噪，易出现排队延迟。

---

## 2. 优化目标

1. 提升扫描吞吐：相同硬件下提高任务并发与阶段完成速度。
2. 降低相互影响：Web 重任务、AI 去噪、常规任务互不“拖慢”。
3. 提高可观测性：能明确看到“哪个队列/容器”成为瓶颈。
4. 平滑升级：先做低风险拆分，再逐步引入代码级队列重构。

---

## 3. 方案总览（推荐分三阶段）

| 阶段 | 改动级别 | 是否改代码 | 预期收益 | 风险 |
|---|---|---|---|---|
| Phase A | 容器拆分（按现有队列） | 否 | 立刻降低单容器负载，提升稳定性 | 低 |
| Phase B | AI 队列独立（`arlai`） | 是（小改） | AI 去噪不再与 Web 重任务抢队列 | 中 |
| Phase C | 深度解耦与弹性扩缩 | 是（中改） | 吞吐进一步提升，容量治理更精细 | 中高 |

---

## 4. Phase A（优先落地，低风险）

### 4.1 核心思路

不改变现有任务分发逻辑，只把“一个 `arl_worker` 同时跑 4 队列”改成“多个 worker 容器各跑各的队列”。

### 4.2 拆分建议

1. `worker_task`：仅消费 `arltask`
2. `worker_heavy`：仅消费 `arlheavy`
3. `worker_web`：仅消费 `arlweb`
4. `worker_github`：仅消费 `arlgithub`

这样做后：

1. 某个队列爆发（例如 `arlweb`）不会拖死其它队列。
2. 容器维度可单独限流/扩容/重启。
3. 日志与告警定位更清晰（直接定位到具体容器）。

### 4.3 `docker-compose` 参考（示意）

```yaml
services:
  worker_task:
    image: arl:local
    container_name: arl_worker_task
    restart: unless-stopped
    entrypoint: ["sh", "-c", "wait-for-it.sh -t 0 mongodb:27017; wait-for-it.sh -t 0 rabbitmq:5672; wait-for-it.sh -t 0 redis:6379; celery -A app.celerytask.celery worker -l info -Q arltask -n arltask@%h -c 2 -O fair -f /code/logs/arl_worker_task.log"]
    volumes:
      - ./config-runtime.yaml:/code/app/config.yaml
      - ./image:/code/app/tmp_screenshot
      - ./logs:/code/logs
      - ../../tools:/code/tools:ro

  worker_heavy:
    image: arl:local
    container_name: arl_worker_heavy
    restart: unless-stopped
    entrypoint: ["sh", "-c", "wait-for-it.sh -t 0 mongodb:27017; wait-for-it.sh -t 0 rabbitmq:5672; wait-for-it.sh -t 0 redis:6379; celery -A app.celerytask.celery worker -l info -Q arlheavy -n arlheavy@%h -c 2 -O fair -f /code/logs/arl_worker_heavy.log"]

  worker_web:
    image: arl:local
    container_name: arl_worker_web
    restart: unless-stopped
    entrypoint: ["sh", "-c", "wait-for-it.sh -t 0 mongodb:27017; wait-for-it.sh -t 0 rabbitmq:5672; wait-for-it.sh -t 0 redis:6379; celery -A app.celerytask.celery worker -l info -Q arlweb -n arlweb@%h -c 3 -O fair -f /code/logs/arl_worker_web.log"]
```

## 5. Phase B（建议作为重点优化）

### 5.1 问题点

当前 AI 去噪在 `arlweb` 队列，与目录扫描、nuclei、afrog 等 Web 重任务混跑，容易出现：

1. 扫描完了但 AI 去噪迟迟未落库。
2. AI 调用超时/重试反过来占用 Web 队列槽位。

### 5.2 目标改造

新增独立队列：`arlai`，专门承载 `AI_DENOISE_TASK / AI_DENOISE_MODULE_TASK`。

### 5.3 实施要点

1. Celery 新增 `@celery.task(queue='arlai')` 入口（如 `arl_task_ai`）。
2. `_enqueue_ai_denoise_task` 从 `arl_task_web.delay(...)` 改为 `arl_task_ai.delay(...)`。
3. 新增容器 `worker_ai` 仅消费 `arlai`。
4. 新增配置项：
   - `CELERY_AI_WORKER_CONCURRENCY`
   - `AI_DENOISE_REQUEST_QPS`（可选，限制外部模型请求速率）
   - `AI_DENOISE_RETRY_BACKOFF_SEC`（可选，失败退避）

### 5.4 预期收益

1. AI 去噪延迟更可控，不再受 Web 扫描峰值强影响。
2. 扫描与去噪各自可独立扩容。
3. 故障域更小：AI 供应商波动不会拖慢 Web 重任务队列。

## 6. Phase C（中长期演进）

可在业务稳定后继续拆分以下能力：

1. `worker_poc`：nuclei/afrog 专用
2. `worker_capture`：截图/爬虫专用
3. `worker_intel`：WIH/URL 探测专用

同时引入“按队列弹性扩容”：

1. 依据 RabbitMQ backlog 自动调整副本数（K8s 或 Compose 扩容脚本）。
2. 高峰时临时提升 `worker_web / worker_ai` 副本，低峰回收。

---

## 7. 观测与验收指标

建议至少观测以下指标（按队列、按容器）：

1. Queue backlog：`messages_ready / messages_unacked`
2. 任务排队时长：从 `dispatch_time` 到 `start_time`
3. 阶段耗时：`service[].elapsed`（重点看 `site_spider / file_leak / nuclei_scan / web_info_hunter`）
4. AI 去噪落库延迟：任务 `end_time` 到 `ai_denoise_status.updated_at`
5. 容器资源：CPU、RSS、I/O wait
6. 错误率：Celery task exception、AI 调用失败率

验收建议（可作为阶段门槛）：

1. `arlweb` 队列 backlog 峰值下降 30% 以上。
2. AI 去噪平均落库延迟下降 40% 以上。
3. 主任务完成后 10 分钟内 AI 去噪落库覆盖率达到 95%+（按已启用模块统计）。

---

## 8. 回滚策略

1. 保留旧 `arl_worker` 定义（或保留同等一键切换脚本）。
2. 新拆分容器先灰度 1 台环境验证，再全量切换。
3. 若出现异常，回滚为单容器多队列模式，确保业务连续性。

---

## 9. 推荐落地顺序

1. 先做 Phase A：不改代码，低风险，快速见效。
2. 再做 Phase B：把 AI 去噪独立为 `arlai` 队列，解决当前主要冲突点。
3. 最后按容量再评估 Phase C 是否必要。
