# AI渗透测试浏览器增强与认知图谱规划

## 1. 文档目的

本文件用于规划 `AI+MCP 渗透测试` 的下一阶段重点能力：

1. 引入“浏览器增强”能力，让 AI 不再只依赖 `httpx/http_req` 这一类 HTTP 级工具  
2. 引入“认知图谱”能力，让 AI 不再只是线性消费前期信息收集结果  
3. 明确 `JS 接口提取`、`认证上下文`、`弱口令/验证码` 等边界与发展方向  

本文件是对以下文档的补充与细化：

- [AI渗透测试基础能力矩阵规划.md](./AI渗透测试基础能力矩阵规划.md)
- [AI渗透测试与MCP开发规划.md](./AI渗透测试与MCP开发规划.md)
- [开发规范.md](./开发规范.md)

## 2. 当前问题

当前 `AI渗透测试` 已经可以使用前期信息收集结果，包括：

- 站点
- IP
- 服务
- 目录扫描
- URL 信息
- 风险
- PoC 风险
- 指纹

并结合：

- `OWASP / PortSwigger` 风格基础能力
- `AI + MCP` 规划/验证
- `PoC 文库` 知识索引增强
- `API 文档 + JS 提取接口` 的结构化消费

但与真正的渗透测试工程师相比，仍存在明显差距：

### 2.1 主要依赖 HTTP 级请求

当前更多依赖：

- `utils.http_req`
- `httpx`
- 少量参数重放 / 结构化探针

问题在于：

- 很多站点是 SPA / 前后端分离应用
- 登录页、工作台、后台往往依赖动态加载 JS
- 真正的接口、参数、鉴权方式、前端逻辑链，并不都能通过纯 HTTP 请求直接看清

例如：

- 某个登录页到底加载了哪些 JS
- 这些 JS 是否暴露了接口路径
- 是否存在未授权资源
- 是否在运行时拼装了 API Base URL / Token Header / 路由参数

这类信息，仅靠 `httpx/http_req` 难以完整拿到。

### 2.2 缺乏“认知图谱”

当前 AI 更像：

- 收到一条风险
- 重放一下
- 跑一个探针
- 给出结论

而真实渗透测试工程师更像：

- 把目录扫描、URL、页面、接口、指纹、风险、PoC 命中、JS、认证点、对象 ID 点联系起来
- 形成一个关于目标的“认知图谱”
- 再决定下一步测哪里

当前系统还不具备这种“多信息点关联推理”的能力。

## 3. 下一阶段目标

## 3.1 浏览器增强目标

让 AI+MCP 在高价值目标上具备接近浏览器代理测试的视角，包括：

- 页面真实渲染后的资源加载情况
- 动态 JS 请求链
- 接口调用顺序
- 前端路由 / Hash / Query 变化
- DOM 中出现的真实表单、按钮、接口触发器
- 运行时产生的接口面、参数面、认证线索

## 3.2 认知图谱目标

让 AI 不再只消费“单条记录”，而是围绕一个目标构建图谱：

- 资产节点：站点、IP、服务、目录、URL、JS、接口、风险、PoC风险
- 关系边：引用、跳转、加载、调用、命中、同源、同参数、同对象引用

让 AI 的验证顺序基于图谱推理，而不是基于单条风险的局部判断。

## 4. 浏览器增强方案

## 4.1 是否需要引入无头浏览器

结论：需要，但不能替代现有 HTTP 级探测。

建议采用“双层执行模型”：

### 第一层：轻量 HTTP 验证（默认）

适用范围：

- 普通站点
- 低价值目标
- 已有较强结构化上下文的目标

优点：

- 快
- 内存低
- 并发高
- 不容易被浏览器特征检测

### 第二层：浏览器增强验证（高价值目标）

触发条件建议：

- 目标命中高价值画像
- 前端为 SPA / JS 重度驱动
- 仅靠 HTTP 难以看清接口面
- 登录页 / 管理后台 / 工作台 / 富交互页面
- 需要真实资源树、请求树、表单树

优点：

- 接近真实浏览器视角
- 可以看到动态加载链
- 能更完整提取 JS 接口、运行时参数、前端认证逻辑

## 4.2 性能问题

无头浏览器确实比 `httpx` 慢，也更吃内存。

因此不建议：

- 默认所有目标都用浏览器
- 浏览器参与批量扫描

建议策略：

### 浏览器仅用于高价值目标

默认触发阈值可参考：

- `AI判定高价值`
- `api_surface_summary` 不充分
- `JS命中较多但接口面不清晰`
- `登录页/后台页/工作台页`

### 浏览器任务单独限流

建议配置项：

- `BROWSER_INTEL_ENABLE`
- `BROWSER_INTEL_MAX_TARGETS_PER_TASK`
- `BROWSER_INTEL_MAX_CONCURRENCY`
- `BROWSER_INTEL_TIMEOUT_SEC`
- `BROWSER_INTEL_MEMORY_BUDGET_MB`

### 浏览器结果可缓存

对于同一任务中的同一 URL，可缓存：

- 资源树
- JS 清单
- API 请求清单
- 表单结构
- 页面截图

避免重复加载页面。

## 4.3 反爬/WAF 检测问题

无头浏览器会带来额外风险：

- `navigator.webdriver`
- Chrome Headless 特征
- 行为模式过于机械
- JS Challenge / WAF 指纹识别

建议策略：

### 不追求“全面 stealth”

不建议在当前阶段做：

- 大量浏览器反检测对抗
- 深度伪装浏览器指纹
- 激进的人类行为模拟

因为这会明显推高复杂度与风险。

### 只做“低侵入浏览器采集”

浏览器增强当前目标应限定为：

- 获取页面资源树
- 获取运行时 JS 列表
- 获取 XHR/fetch 请求清单
- 获取表单与 DOM 结构
- 获取前端暴露接口与参数

而不是：

- 模拟复杂点击流
- 自动绕过挑战
- 自动突破强风控

## 5. JS 接口提取策略

## 5.1 规则提取仍然是主力

当前已经有一部分规则提取能力，后续仍应保留为主干：

- `fetch(...)`
- `axios.get/post(...)`
- `$.ajax(...)`
- `XMLHttpRequest.open(...)`
- `params/data/body/URLSearchParams`

原因：

- 成本低
- 可解释
- 稳定
- 易测试

## 5.2 AI 参与提取，但只做增强层

AI 可以参与的部分：

- 补全复杂拼装 URL
- 补全变量映射后的路径
- 提取规则难以覆盖的接口描述
- 判断接口用途（auth/object-id/upload/download）

不建议让 AI 直接替代规则做全量提取。

建议模式：

### `Rule First + AI Refine`

1. 规则先提取：
- 接口 URL
- method
- params
- source js

2. AI 再做增强：
- 变量归因
- 路由推断
- 认证方式提示
- 对象引用/文件处理/管理能力分类

这样既稳定，又能吃到 AI 的推理能力。

## 5.3 统一成 `api_surface_summary`

无论来源于：

- API 文档
- JS 提取接口
- 浏览器运行时请求树

最终都统一归并为：

- `path_count`
- `sample_paths`
- `auth_path_count`
- `auth_paths`
- `parameter_names`
- `security_scheme_count`
- `object_id_like_count`
- `upload_like_count`
- `download_like_count`
- `js_api_count`
- `sample_interfaces`
- `source_types`

未来浏览器增强产物也应并入这套结构，而不是单独发明一套字段。

## 6. 认知图谱方案

## 6.1 为什么要做认知图谱

真实渗透测试工程师不会把信息点割裂看待。

例如：

- 某目录扫描发现 `/swagger-ui/index.html`
- 某 JS 又暴露 `/api/user/detail?id=`
- 某 URL 信息里有 `/login`
- 某风险里命中 `JWT`

这些点连接起来以后，推理结果应该是：

- 这是一条“有鉴权、有对象 ID、有接口面”的系统
- 应优先做：
  - auth 入口识别
  - token/jwt 分析
  - object reference / IDOR

这就是图谱能力。

## 6.2 图谱对象模型

建议节点类型：

- `site`
- `path`
- `url`
- `js`
- `api_endpoint`
- `form`
- `risk`
- `nuclei_result`
- `wih_record`
- `service`
- `fingerprint`

建议关系类型：

- `loads`
- `calls`
- `references`
- `same_origin`
- `same_param_family`
- `same_object_reference`
- `auth_related`
- `file_related`
- `came_from`

## 6.3 图谱的最小用途

第一阶段不需要做复杂图数据库。

可以先做“任务级内存图谱 / JSON 图谱摘要”：

- 每个任务构建一份图谱摘要
- AI planner 消费图谱摘要
- 详情页展示部分图谱结果

建议产物：

- `task_ai_pen_graph`
- `node_count`
- `edge_count`
- `top_paths`
- `top_params`
- `auth_cluster`
- `file_cluster`
- `object_ref_cluster`

## 7. 关于弱口令与验证码

## 7.1 弱口令能力的位置

弱口令/口令验证属于渗透测试基础能力的一部分，但不建议默认并入 AI 渗透主链。

原因：

- 副作用高
- 合规边界更敏感
- 很容易影响业务

建议定位：

- 独立受控模块
- 仅在显式开启时参与
- 必须带审计
- 必须可限速、可熔断

## 7.2 验证码问题

验证码本身当然是渗透测试的一部分，但在当前阶段：

不建议做：

- 自动识别验证码并持续绕过
- 自动尝试对抗图形/滑块/行为验证码

建议做：

- 检测“是否存在验证码 / 类验证码”
- 将其作为认证防护特征记录
- 若用户显式提供登录态或测试会话，则继续后续验证

可以做的安全增强是：

- 识别验证码存在
- 识别验证码接口
- 判断验证码是否只在前端做弱校验

而不是自动化绕过。

## 8. 建议的下一阶段研发顺序

### M1：浏览器情报采集层

目标：

- 浏览器增强获取资源树、表单树、请求树、JS 清单

产出：

- `browser_surface_summary`
- `runtime_api_calls`
- `dom_form_summary`

### M2：认知图谱层

目标：

- 将目录、URL、JS、接口、风险、PoC 风险联结成图谱摘要

产出：

- `task_ai_pen_graph_summary`

### M3：能力矩阵与场景映射融合

目标：

- 让 AI planner / verifier 基于图谱和能力矩阵工作

### M4：产品画像只做偏置

目标：

- 只调优优先级和顺序
- 不主导验证框架

### M5：文库继续增强

目标：

- 文库只补入口、动作、证据、别名
- 不替代基础能力主干

## 9. 一句话结论

下一阶段的重点不应是“继续堆产品或 PoC”，而应是：

1. 用浏览器增强补足前端与运行时视角  
2. 用认知图谱把分散的信息点连起来  
3. 让 AI 渗透测试基于基础能力矩阵、场景映射和图谱推理工作  

这样 AI+MCP 才会更接近真正的渗透测试工程师。
