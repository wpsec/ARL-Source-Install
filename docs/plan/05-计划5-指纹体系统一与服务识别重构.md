## 一、目标

- 将站点识别和服务识别的指纹来源统一为规范 JSON。
- 降低通用关键字、单端口和单字段命中造成的误报。
- 保留现有 HTTP API、Mongo 文档结构和用户自定义指纹能力。
- 保留 Kscan 指纹规则，但不将 Kscan 作为独立网络扫描器运行。
- 避免 Nmap、NPoC 对同一服务进行无条件重复识别。

本计划只涉及指纹体系和服务识别，不替换 Nmap，不新增主动协议探针。

## 二、性能优化与技术选型

### 2.1 优先级

指纹阶段的优化顺序固定为：

```text
减少重复请求
    → 规则预编译与索引
    → 批量匹配与结果去重
    → Rust CPU 加速
    → 受控并发与调度优化
```

Rust 不是扫描速度的唯一解决方案。若时间主要消耗在 HTTP、Playwright、DNS、Nmap 或 NPoC 等网络和外部进程等待，单纯重写匹配逻辑不会明显降低端到端耗时。

### 2.2 推荐技术路线

| 优化方向 | 推荐方法 | 适用范围 |
|---|---|---|
| 响应复用 | 任务级 `ResponseRegistry`、连接池、同 profile 缓存 | 页面、JS、API 文档和站点识别 |
| 规则匹配 | 启动时编译规则，按字段建立倒排索引 | 站点和服务指纹 |
| CPU 加速 | Rust + PyO3 批量匹配、归一化、去重和证据聚合 | 大批量响应或服务结果 |
| Python 调度 | 保留 Python `asyncio`/线程池和现有 WAF、预算、重试策略 | 网络请求和任务编排 |
| 外部扫描 | 保留 Nmap/NPoC，先做阶段基准再评估替代工具 | 端口和协议识别 |

不建议在本阶段引入完整 Rust HTTP 客户端、Rust Mongo 驱动或重写 Nmap。它们会扩大边界，但不能直接解决指纹误报和重复识别问题。

### 2.3 规则索引

规范 JSON 仍作为交换和发布格式，运行时不得对每个响应遍历全部规则。加载后建立进程级索引：

- `icon_hash` 精确值索引；
- Header 名称和值的规范化 token 索引；
- Title、Body、Response 中稀有字面量索引；
- URL 路径段和前缀索引；
- Regex 规则单独编译，仅对索引筛选后的候选执行；
- `excludes` 和禁用规则提前建立拒绝集合。

匹配流程：

```text
响应
  → 字段归一化
  → 倒排索引召回候选规则
  → all/any/excludes 证据判断
  → 置信度计算
  → confirmed/candidate/discarded
```

这样可以把“全量规则扫描”变为“候选规则扫描”。索引命中不能改变结果语义，索引遗漏候选时必须有受控 Python 全量回退或构建期校验。

**召回保障（评审修订，正确性关键）**：纯 regex 规则（无公共字面量锚点，如 `/\bnginx\/[\d.]+/`）不会进入任何字面量倒排桶，"仅对索引筛选后的候选执行 regex"对其不成立。定死两条：

1. 生成期对每条 regex 提取必含字面量（前缀/必需子串）作锚点；提取失败的规则归入 **no-anchor 兜底桶**，对每条响应恒执行（接受 O(桶大小) 成本，桶容量进 §2.6 观测并设告警阈值）。
2. 构建期 golden 校验必须覆盖兜底桶路径（构造仅兜底可命中的样本），"索引结果＝全量 Python 结果"的一致性测试对含无锚点规则的语料成立后才允许启用索引。

### 2.4 Rust 加速边界

Rust 只承载无副作用、可批处理的 CPU 逻辑：

- 页面 Header、Body、Title、URL、Icon Hash 的批量匹配；
- Nmap/NPoC 服务名称和别名归一化；
- 候选规则过滤、评分、排序和去重；
- 多来源证据合并和规范化结果计算。

推荐批量接口：

```text
输入：响应集合或 Nmap/NPoC 结果集合、已编译规则索引、匹配选项
输出：规范化结果集合、证据集合、每批 metrics
```

要求：

- 不逐条执行 FFI；
- 规则索引按文件 hash 缓存，规则变更时整体重载；
- Rust 不访问 Mongo、Redis、Celery、HTTP、DNS、Playwright 或外部扫描器；
- Rust 导入失败、单批异常或结果校验失败时，仅当前批次回退 Python；
- fallback 日志包含 `stage`、`batch_id`、异常类型、输入数和输出数。

### 2.5 网络和端口扫描边界

- 页面、JS 和 API 文档优先复用任务内响应，减少重复 HTTP 请求；
- 每个流量类别使用独立连接池、并发度、超时和 WAF 熔断器；
- Nmap 继续负责端口发现和可选 `-sV`；
- NPoC 只补充 Nmap 未识别或低置信度端口；
- 不默认无限提高网络并发；
- `masscan`、`naabu`、`RustScan` 等端口工具只有在独立基准证明准确率和完整性可接受后，才进入替代方案评估，不在本计划中直接替换 Nmap。

### 2.6 性能观测

迁移前后必须分别记录：

- 规则加载和索引构建耗时；
- 单批响应数、规则候选数、实际匹配数；
- Python 匹配 CPU 时间、Rust 匹配 CPU 时间和墙钟时间；
- HTTP 总请求数、唯一请求数、缓存命中数和重复请求数；
- Nmap/NPoC 目标数、重复识别数和等待时间；
- confirmed、candidate、discarded 数量；
- fallback 次数、原因和批次。

未完成基准前不得宣称 Rust 提升了扫描速度。

| 来源 | 当前用途 | 处理方式 |
|---|---|---|

## 五、站点指纹规范

站点指纹采用证据型 JSON 格式：

```json
{
  "meta": {
    "format": "arl_site_fingerprint_v1",
    "generated_at": "...",
    "source_count": 0,
    "rule_count": 0
  },
  "fingerprints": [
    {
      "id": "site:nginx",
      "name": "Nginx",
      "category": "server",
      "match": {
        "any": [
          {
            "all": [
              {
                "field": "header",
                "operator": "contains",
                "value": "server: nginx"
              }
            ]
          }
        ]
      },
      "confidence": 82,
      "sources": ["webapp", "tools_finger"],
      "enabled": true
    }
  ]
}
```

支持字段：

- `body`
- `header`
- `title`
- `response`
- `url`
- `icon_hash`

支持操作：

- `contains`
- `equals`
- `regex`
- `all`
- `any`
- `excludes`

误报控制：

- 仅命中端口、通用标题或通用正文关键字时，只能产生候选结果。
- `icon_hash`、精确 Header、URL 路径和多字段组合可提高置信度。
- `excludes` 命中时不得输出确认结果。
- 同名规则合并时保留 `sources`、`match_fields` 和命中规则数量。
- 低置信度结果继续进入候选集合，不直接覆盖确认结果。

## 六、服务指纹规范

服务指纹采用 Nmap/NPoC 结果映射格式：

```json
{
  "meta": {
    "format": "arl_service_fingerprint_v1",
    "generated_at": "...",
    "source_count": 0,
    "rule_count": 0
  },
  "fingerprints": [
    {
      "id": "service:http",
      "name": "http",
      "protocol": "tcp",
      "aliases": ["http", "www", "https", "ssl/http"],
      "ports": [80, 443],
      "matchers": [
        {
          "field": "nmap.service_name",
          "operator": "equals",
          "value": "http",
          "weight": 90
        },
        {
          "field": "npoc.scheme",
          "operator": "equals",
          "value": "http",
          "weight": 100
        }
      ],
      "confidence": 90,
      "sources": ["nmap", "npoc"],
      "enabled": true
    }
  ]
}
```

服务指纹只负责：

- 服务名称和别名归一化；
- 协议、端口、产品、版本字段规范化；
- Nmap/NPoC 结果的置信度和来源合并；
- 冲突结果的优先级处理。

服务识别优先级：

1. NPoC 明确协议结果；
2. Nmap 明确服务名称；
3. Nmap 产品和版本信息；
4. 端口号仅作为弱候选，不能单独确认服务。

Nmap 底层 `nmap-service-probes` 不复制到仓库，继续由 Nmap 负责执行。

### 第2阶段：统一指纹生成脚本

扩展现有指纹构建脚本，支持读取：

- `webapp.json`；
- `tools/finger.json`；
- Kscan JSON；
- Mongo 导出规则；
- `name + human_rule` 标准规则。

脚本生成两个规范 JSON，并输出：

- 输入文件统计；
- 有效、重复和无效规则数量；
- 被排除规则及原因；
- 规则冲突；
- 每条规则的来源；
- 规范化前后差异。

同时生成或构建运行时索引校验结果，确认每条规范规则都能被索引召回；索引属于运行时产物，不替代两个 JSON 发布文件。

生成过程必须确定性排序，支持 `--dry-run` 和 golden 对比。

### 第3阶段：站点识别收敛（收编式，见§零.1）

- `SiteFingerprintRegistry` / `SiteFingerprintMatcher` 在 `fingerprint_cache` 既有合并/置信度语义之上增量构建：Matcher 的 all/any/excludes 证据判断与 confirmed/candidate 分类**复用** `split_fingerprint_result_items` 一族函数，Registry 只新增倒排索引层；禁止第二套 confidence 计算。
- Registry 启动时加载规范 JSON 并构建倒排索引，Matcher 只对候选规则执行完整证据判断。
- 消灭双路径：`fetchSite.py` 对 `utils/fingerprint`（import 期模块级加载 webapp.json 的 legacy 加载器）的直接依赖切断，统一走 Registry；`utils/fingerprint.py` 随第7阶段清理评估下线。
- 旧规则、Kscan 规则和 Mongo 规则先编译，再统一匹配。
- Wappalyzer 作为动态证据独立参与合并，不直接覆盖静态结果。
- 保留现有确认结果、候选结果和 Mongo 字段。
- 先完成 Python 索引版，再接入 Rust 批量 Matcher；两者必须使用同一输入和输出契约。

### 第4阶段：Mongo/API 兼容——已按方案(b)变体落地（运行时合并视图，偏离原文"重编译文件"的理由见下）

实现形态：**仓库基线 gz + Mongo 用户规则进程内 merge（SiteFingerprintRegistry overlay）**。
- 保留 `/api/fingerprint` 增删改查/上传/导出，Mongo `fingerprint` 集合 = 用户规则真相源（决策2）。
- 写入口统一在 `finger_db_cache.update_cache(force_db=True)` 尾部 `INCR arl:fingerprint:unified:ver`
  （route 三写点已有该调用，CLI `import_fingerprint` 补齐）；各进程 Registry 60s 版本检查触发重建，
  ver 不可读时 600s 低频对账防丢更新。Redis 关闭则退化为仅文件重建。
- 用户规则**豁免编译期 policy**（`body="login"` 等显式意图保留），只做格式校验（括号/非法条件跳过该条）。
- 冷启动/ Mongo 故障：基线照常服务 + `overlay_unavailable` 显式记录（不空规则启动）。
- 放弃"运行时重编译文件"的理由：compose 实证 `app/dicts` 非共享卷（web/worker 各自镜像文件系统），
  方案(a)需新增挂载且镜像内文件被空卷遮蔽需 seed 复制；多节点部署仍不闭合；启动全量导入需再叠 debounce。
  合并视图把一致性交给已全局部署的 Redis，把"编译规范文件"保留为 `build_unified_fingerprints --mongo-export`
  的发布/审计路径（按需执行，产物入库走 review 流程）。
- 既有限制登记：finger.json 源规则经 sync-fingerprint 启动 upsert 回 Mongo——用户在 UI 删除 finger 来源规则后
  **重启会复活**（legacy 既有语义，本计划不引入删除标记层；如需"删了不复活"需墓碑机制，另立项）。
- 切换口径更新：第4阶段代码就绪 ≠ 放行。`SITE_FINGERPRINT_SOURCE=unified` 上线前置＝x86 容器对照观测
  （unified vs legacy 的 finger/finger_candidates 差异只允许"泛化噪声减少 + faviconhash 摆脱 Mongo 依赖"方向，
  异常聚合名称核对附录B 噪声清单）。

### 第5阶段：服务识别收敛（增量式，见§零.2）

- 新增 `ServiceFingerprintRegistry` 和 `ServiceFingerprintMatcher`。
- 将 Nmap/NPoC 结果统一转换为服务规范结果。
- NPoC 只处理 Nmap 未识别、低置信度或用户明确要求的端口——`_build_sniffer_targets` 智能模式已实现此语义，本阶段不重做门控，只做：门控判定迁入 Registry 规范映射、`full_port` 用户显式选项保持、补幂等键。
- 已被 Nmap 高置信度识别的端口不再无条件调用 NPoC（现状已满足，golden 回归锁定，防退化）。
- 同一 `IP:port + scan_profile` 使用幂等键去重。
- Nmap 与 NPoC 冲突时保留证据和冲突原因，不静默覆盖。
- 服务别名和标准服务名使用索引匹配，端口号只能作为弱候选，不能单独确认服务。

### 第6阶段：Kscan 规则迁移

- 将有效 Kscan 规则转换到 `site_fingerprints.json`。
- 使用 `sources: ["kscan"]` 保留来源信息。
- 不新增 Kscan 网络扫描进程。
- 不把 Kscan 规则误归类为网络服务指纹。
- 本地 Kscan 规则未经 golden 对比不得自动进入生产文件。

### 第7阶段：旧文件清理

只有完成规范文件生成、golden 对比、API 兼容、容器 smoke 和结果回归后，才允许删除旧运行时文件：

```text
ARL/app/dicts/webapp.json
tools/finger.json
ARL/app/dicts/kscan_fingerprint.json
ARL/app/dicts/kscan_fingerprint.local.json
```

删除前必须确认 Kscan 有效规则已进入规范站点文件，且没有运行时加载路径残留。

删除前必须保存迁移统计和规范文件 hash；如果规则转换、索引构建或结果对比失败，只允许保留旧文件并停止清理，不得生成空的规范文件替代旧库。

## 八、测试与验收

### 指纹转换

- 多种旧格式转换测试；
- 重复、冲突、非法表达式和超长关键字测试；
- 来源、类别和规则数量统计测试；
- 规范文件重复生成一致性测试。

### 站点识别

- Header、Body、Title、URL、Icon Hash 命中测试；
- `all/any/excludes` 组合测试；
- 单字段弱命中只能产生候选；
- 多字段命中提高置信度；
- Wappalyzer 与静态规则合并测试；
- Python 旧实现与规范实现 golden 集合对比；
- Python 全量匹配与 Python 索引匹配结果一致；
- Python 索引匹配与 Rust 批量匹配结果一致；
- 有效结果数量不得减少。

### 服务识别

- Nmap 服务名、产品、版本和别名映射测试；
- NPoC 高置信度结果覆盖低置信度 Nmap 结果测试；
- Nmap/NPoC 冲突测试；
- 端口号单独命中只能产生候选；
- 同一 `IP:port` 不重复执行 NPoC；
- 未识别服务保留明确的 unknown/pending 状态。

### 兼容与运行

- `/api/fingerprint` 增删改查、上传和导出兼容测试；
- 用户规则变更后规范文件重新编译测试；
- 编译失败保留上一版文件测试；
- 旧 Mongo 文档读取测试；
- 容器启动加载两个规范 JSON 测试；
- 全仓检查旧文件加载引用；
- 确认不存在 Kscan 独立扫描命令调用。

### 性能与质量

- 规则索引构建结果可重复，索引不能遗漏可命中的规则；
- Rust 热点 p95 CPU 时间降低至少 30%，或吞吐达到 Python 的 1.5 倍；
- 指纹阶段端到端墙钟时间不得因 Rust 接入恶化超过 5%；
- 相同任务内重复 HTTP 请求数不高于基线；
- 已标注样本中，新实现召回率不低于旧实现，精确率不低于旧实现；
- 对每个拥有至少 30 个标注样本的类别，误报率目标较旧实现下降至少 20%；样本不足时只报告结果，不宣称达标；
- 每条确认结果都能追溯到规则 ID、命中字段、来源和匹配批次。

## 九、验收标准

- 运行时只加载一个站点指纹文件和一个服务指纹文件。
- 站点识别有效结果不减少，低证据规则不再直接确认。
- 服务识别的来源、优先级和冲突状态明确。
- Nmap、NPoC 不对同一高置信度端口无条件重复识别。
- Kscan 规则被保留，但不作为独立扫描器运行。
- 现有 HTTP API、Mongo 文档和导出字段不变。
- 规范文件生成可重复、可审计、可回滚。
- 旧指纹文件不再存在运行时加载路径。
- Python 索引版与 Rust 版结果集合一致，Rust 只作为 CPU 加速层。
- 指纹匹配 p95 CPU 或吞吐达到性能门禁，且网络等待没有被错误归因于 Rust。
- 召回率、精确率和误报率均通过标注样本对照，不能只以结果数量判断质量。
- 构建产物、缓存和临时生成文件不进入 Git。

## 十、范围约束

- 不替换 Nmap。
- 不重写 Nmap 底层服务探针库。
- 不新增主动协议探测。
- 不改变现有站点和服务识别公共 API。
- 不把 Wappalyzer、Nuclei 模板直接混入静态站点指纹文件。
- 不在 UI 重构计划中同步改造指纹管理页面，仅保留现有 API 兼容。

## 十点五、决策记录（2026-09-04 用户确认）

1. **Kscan 迁移基准 = `kscan_fingerprint.local.json`（9673 条）**，进生产前置条件：第2阶段 A 的增量审计（1760 条名字新增 + 同名内容强化差异）与 golden 双文件对比通过；上线初期以观测指标（新增确认数、命中 Top 分布）作最终裁决。`kscan_fingerprint.json` 退役为源输入之一。
2. **`tools/finger.json` 定位 = 首次安装种子，Mongo `fingerprint` 集合为用户真相源**：生成脚本以"种子文件 + Mongo 当前态"编译规范文件；用户在 UI 删除的种子规则重编译后不复活。
3. **用户指纹拓展三条入口（收敛后全部保留）**：
   - 单条/少量：UI 指纹管理页或 `/api/fingerprint` 增删改 → Mongo → 触发重编译（hash 去抖，失败保旧版）。
   - 批量文件：放置/替换种子文件 → 启动导入 Mongo（upsert 只增改）→ 重编译生效；文件仅是种子，入库后与 UI 规则同权。
   - 自定义格式：转为 `name + human_rule` 或 finger.json 格式后经 `import_fingerprint` 导入（第2阶段生成脚本的显式输入项）；格式校验失败输出明细，不静默入库。
   - 禁止依赖"直接向容器 dicts/ 塞文件"作为拓展路径（容器重建丢失、多节点不一致）；该目录仅存放构建产物。
