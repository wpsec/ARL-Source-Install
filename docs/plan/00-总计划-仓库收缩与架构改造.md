# 00 总计划：仓库收缩与 Rust + Python 架构改造

## 目标

本轮改造按“三段式目标”推进：

1. 先做一次明确的仓库收缩，彻底移除已废弃的 AI 渗透测试链路及其遗留资产。
2. 再建立 Rust + Python 混合架构，把经过基准确认的 CPU 密集型数据处理迁移到 Rust。
3. 最后推进核心单体解耦，降低 `commonTask`、任务编排、路由直连 Mongo、配置中心和导出链路的复杂度。

Rust 加速链路固定为：

```text
Celery -> Python Orchestrator -> Python Adapter -> Rust 批处理模块 -> WihRecord -> Mongo
```

## 改造边界

本轮保留能力：

- 资产发现主链路
- `WIH`
- URL / JS 增强
- 导出能力
- AI 去噪
- `nuclei / afrog / NPoC` 当前生产能力
- AI 去噪的 PoC 结果复核场景（AI-POC 扫描链本身已于 2026-09-04 经用户决策整体移除，见 03 第五批）

本轮删除能力：

- 旧 AI 渗透测试执行链路
- 本地 MCP runtime
- AI 渗透外部工具白名单执行器
- AI 渗透知识索引
- AI 渗透专属路由、统计、重试、批量运行、导出、前端入口
- `tools/ai_pen_tools`
- `tools/poc`
- 旧 AI 渗透专属 SOP、skill、默认 YAML、测试

## 混合语言架构原则

- Rust 只负责无副作用、可批处理、CPU 密集型逻辑。
- Python 继续负责 Flask、Celery、Mongo、Redis、配置、任务生命周期、网络策略、AI、Playwright 和外部扫描器编排。
- Rust 不直接访问 Mongo、Redis、Celery、LLM、浏览器或外部扫描器。
- Rust 优先处理 URL/JS/HTML 文本提取、URL 归一化、范围过滤、去重、候选排序和指纹计算。
- 现有 Go 版 `tools/wih` 保持不变，不与本轮 Rust 热点迁移混合；是否迁移由后续基准单独决定。
- 所有 Rust 化必须通过结果一致性和性能基准门禁，不能以语言迁移替代瓶颈定位。

## Rust 构建约束

- 新增独立 `ARL/native/arl_accel` PyO3/maturin 模块。
- Rust API 使用批量输入，避免逐条 FFI 调用；Python 现有公共函数签名保持不变。
- 生产镜像同时支持 amd64 与 arm64，使用 release 构建并固定 glibc 兼容下限。
- 主生产 Python 运行时统一按 Python 3.10+ 规划；旧 `ARMWorker/Dockerfile` 的 Python 3.8 仅作为归档路径，不纳入本轮验收。
- 构建必须固定 Rust、PyO3、maturin 版本并提交 `Cargo.lock`；Rust 构建产物、`target/` 和 wheel 缓存不得进入仓库。
- 使用稳定 ABI 和 manylinux/等效兼容构建。PyO3 支持 `abi3` 多版本 wheel，maturin 支持 manylinux 与跨架构构建。[PyO3 构建与分发](https://pyo3.rs/main/building-and-distribution)、[Maturin 分发与跨编译](https://www.maturin.rs/distribution.html)

## 关键原则

- 本轮是收缩式改造，不做旧 AI 链路的新旧双轨并行。
- 删除项直接退场，不保留兼容接口和历史只读查询。
- 在进入核心架构重构前，先修复当前任务执行的性能、预算和统计基线。
- 性能顺序固定为：基线采集 -> Rust 接口抽象 -> Rust 实现 -> Python 接入 -> 架构解耦。
- Rust 加载失败或单批异常时，必须记录原因并按当前批次回退 Python；禁止静默降级。
- 先清理废弃能力，再做 Rust 热点抽取，不让 Rust 模块依赖待删除代码。
- 每一批必须可独立测试、独立回归、独立发布。
- 文档、配置、代码、前端入口和构建链必须同步收口，避免“功能已删但入口仍在”。

## 性能治理主线

本轮性能治理与语言迁移并行但分层验收，先解决外部 IO、串行阶段和任务状态不可见问题，再扩大 Rust CPU 热点范围。

- 扫描采用同一 Task ID 下的双层异步语义：发现阶段先规范化、聚合并落库，深度阶段进入可恢复队列；首批可用域名、IP、站点结果目标为 5 分钟内可见，最终 `done` 只表示深度链路已清空。
- 全任务不设置硬截止时间，但阶段、provider、批次、目标和外部程序必须有独立预算；任何失败都必须落为 `failed`、`degraded` 或 `pending`，不得用空结果伪装成功。
- `test/top100/top1000/custom` 严格使用用户选择的端口集合；`all` 严格完成 `0-65535`，可以先展示初筛结果，但不能用常用端口结果替代最终结果。
- 端口扫描在具备 `CAP_NET_RAW` 时优先使用 `nmap -sS`；权限不足只允许按当前批次明确记录原因并回退 `-sT`，不得静默改变扫描方式。`all` 模式按单 IP 批次执行，默认 4 路且不超过 4 路受控并发，并在每批完成后更新指标。
- 已确认属于 CDN 的 IP 默认跳过 IP 端口扫描，不把 CDN 边缘节点的 80/443 伪造成开放端口；站点发现仍基于业务域名执行 HTTP/HTTPS 探测。疑似“全端口开放”主机保留原始端口结果，但跳过高成本的逐端口服务识别并标记可疑状态。
- 站点探测仅对端口阶段已确认关联公网 IP 的业务域名，放行“解析器与系统解析均为公网但无交集”的负载均衡/DNS 视图漂移；私网地址、未确认关系和其它 DNS policy 失败仍拦截，并记录例外与降级计数。
- provider 先做全局候选规范化和去重，再按 provider 使用独立并发度、连接/读取超时、有限重试和熔断；代理仅作为配置后的兜底，端口扫描不经过 HTTP 代理。
- 来源聚合只去重结果，不丢失 `source/sources` 关系；批次失败、待处理数量和降级原因必须可追溯。
- 40 个目标用于定位 `port_scan`、provider、文件泄漏、WIH 和 Nuclei 的瓶颈；64 个目标使用相同配置执行 Rust 开关对照，作为最终 p95 和结果完整性门禁。
- 性能结论区分墙钟、CPU、网络等待、内存和结果数量；网络 IO 占主导时不强行归因于 Rust。

## 统一发现上下文与跨工具协同

扫描性能治理的第一优先级是消除工具之间的重复请求和数据断链，而不是继续扩大 Rust 覆盖范围。

- 每个 Task ID 建立一个 `WebAssetScanOrchestrator` 和一个 `DiscoveryContext`，由上层统一编排站点获取、爬虫、URLFinder、WIH、目录扫描和 URL 探测。
- `DiscoveryContext` 包含任务内热响应注册中心、候选资产注册中心、事件分发、来源聚合、WAF 流量隔离和幂等状态；持久化账本只保存可恢复状态与结果元数据，不能让 Redis 成为业务结果唯一事实源。
- 页面响应遵循“一次获取，多方消费”：爬虫、URLFinder、WIH、站点识别和 URL 探测优先消费同一任务内响应，不因不同工具再次请求同一 URL。
- 候选遵循“一次发现，全链路分发”：新页面、新 API、新 JS、新目录和新子域统一进入候选图，再按类型分发给相应策略，保留完整 `sources` 关系。
- Python 爬虫、URLFinder、WIH 和目录扫描仍是独立策略，不合并成无法隔离预算和失败状态的单体扫描器；共享的是响应、候选、调度和结果协议。
- 目录扫描使用独立流量类别和 WAF 熔断器。目录请求触发的疑似 WAF 只能暂停目录队列，不能连坐熔断正常爬虫和 WIH；只有确认主机级封禁时才暂停站点全部请求。
- 候选状态必须区分 `discovered`、`queued`、`fetching`、`fetched`、`covered`、`failed`、`degraded`、`pending` 和 `skipped`，不能用“出现过 URL”代替“已经完成内容处理”。
- Rust 暂不重写整个 WIH，仅在统一响应和候选数据流稳定后，继续作为 HTML/JS/URL 解析、过滤、排序、去重和指纹计算的后置加速层。

## 风险项

- `commonTask.py` 中 AI 渗透逻辑与 `AI-POC`、`nuclei / afrog` 编排存在历史耦合，删除时要严格区分保留与废弃路径。（2026-09-04 落地：AI-POC 链与僵尸 `penetration_scan` 模块整体移除，nuclei/afrog 回落默认参数路径，AI 去噪/WIH 填充不受影响。）
- `api_console.py`、`export.py`、`App.tsx` 中存在大量配置与展示耦合，必须前后端一并清理。
- 启动流程导入即执行副作用已收口：`arl_update` 移出 `app.main` 导入期，生产由 `start_web.sh` 在 gunicorn 前显式调用 `app.tools.arl_bootstrap`，开发直跑在 `__main__` 保留同语义；worker 导入路径本就不经过 `main.py`。
- Rust FFI 的批量数据转换、异常边界和多架构构建可能引入结果差异或部署失败。
- 仓库内存在历史构建产物与大体积资料目录，删除后要重新验证引用关系。

## 冻结规则

- 本轮计划以 `docs/plan/00-*` 到 `docs/plan/04-*` 为唯一现行方案。
- `docs/history/Strix-cn集成重构计划.md` 视为归档文档，不再引用为实施依据。
- `docs/plan/WIH提速与调度优化实施计划.md` 继续作为 WIH 调度专项方案，仅由 `02` 和 `03` 引用。
- 在完成第 1 阶段废弃能力清理前，不新增任何替代 AI 渗透链路。
- 本轮只对统一数据流中的纯数据热点做 Rust 加速，不直接重写 Go WIH；全 Rust WIH 方案暂停，后续是否恢复必须重新立项。
