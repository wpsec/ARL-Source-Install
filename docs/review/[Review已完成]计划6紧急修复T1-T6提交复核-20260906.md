## 三、阻断项

### R6-P0-01：桥接层绕过 Endpoint 范围拒绝

证据：[`api_candidate_registry.py:1041-1054`](../../ARL/app/services/api_candidate_registry.py:1041)。

`_bridge_parse_result()` 先调用 `register_endpoint(endpoint)`，但忽略返回值，随后无条件调用 `endpoint.to_legacy_records()` 并执行 `_append_record()`。当 Registry 因 host 越界拒绝 Endpoint 时，旧记录面仍会得到：

```text
api_doc_endpoint  METHOD https://out-of-scope.example/...
urlfinder_url     https://out-of-scope.example/...
```

最小复现结果：`registry=[]`，但 `scanner.records` 含上述两条记录。这样“越界不注册、不 fetch、只计数”的契约只在新 Registry 面成立，旧记录消费者仍可能继续消费越界 URL，范围闸不是真正的统一出口。

修复要求：

- 桥接层必须区分“注册成功/重复命中”和“越界拒绝”，只有前两者允许生成 legacy adapter 记录。
- 被拒绝的 Endpoint 只计 `api_endpoint_out_of_scope_total` 及必要诊断，不进入 `scanner.records`、候选图和补探输入。
- REST、GraphQL、SOAP 各补一条桥接端到端测试；测试必须同时断言 Registry、legacy records、candidate graph 均无越界资产。
- 不要通过“先写旧记录、后续再过滤”修复，这会继续把范围责任分散到消费者。

### R6-P1-01：lease 缺少所有权 fencing，旧回报可覆盖新 claim

证据：[`api_candidate_registry.py:455-467`](../../ARL/app/services/api_candidate_registry.py:455)、[`api_candidate_registry.py:469-486`](../../ARL/app/services/api_candidate_registry.py:469)、[`api_candidate_registry.py:501-531`](../../ARL/app/services/api_candidate_registry.py:501)；编排回收位于 [`wih_orchestrator.py:208-223`](../../ARL/app/services/wih_orchestrator.py:208)。

当前只按 `scoped_key -> deadline` 记录 claim，没有 claim id 或 generation。复现顺序：

```text
worker A claim      -> queued
lease 到期回收      -> pending
worker B claim      -> queued
worker A 回报结果   -> B 的同一对象被改成 covered
worker A finally    -> 也可能把 B 的对象改回 pending
```

这会造成重复探测、错误归因和状态回退。`finally` 只能保证“有回收动作”，不能证明回收动作属于当前 owner。

修复要求：

- claim 时生成不可复用的 claim token 或单调 generation，并随返回句柄传给 probe 回报与 finally。
- `probe_report`、`mark_endpoint` 的消费路径和 `requeue_unreported` 必须校验 token；过期 owner 的回报只能 no-op，并计 stale-report 指标。
- 增加“旧 claim 到期后新 claim，再提交旧 report/finally”的并发/时序测试。
- 继续保持“Registry 为进程内非持久化结构”的边界声明；token fencing 解决的是同一 Registry 内的并发所有权，不等于跨 Celery 持久化恢复。

### R6-P1-02：请求形态摘要截断导致错误合并

证据：[`api_candidate_registry.py:1312-1325`](../../ARL/app/services/api_candidate_registry.py:1312)。

`param_names/query_names/json_keys/form_keys` 各自只保留前 32 项，最终又对 JSON 字符串取前 4096 字节。两个请求只要前缀相同、差异落在截断区域，就会得到相同 `input_signature`。最小复现使用 32 个相同 JSON key，再分别添加 `zz_a` 和 `zz_b`，结果为 `created_a=1、created_b=0、assets=1`。

这不泄露参数值，但违反“不同形态分离”的身份契约。

修复要求：

- 限制资源消耗时不能直接把截断前缀作为完整身份；应加入完整名称集合的有界 overflow digest，或对所有名称做流式 hash 后仅保存摘要。
- 摘要中可保留 `truncated`/`overflow_hash`，但 `input_signature` 必须区分截断区域不同的请求。
- 增加 33 个 key、超 4096 字节名称、只在尾部变化三组测试；仍需断言取值、Cookie、Authorization 不进入签名。

## 四、重要兼容项

### R6-P2-01：新增 `observed_url` 改变 dataclass 位置参数语义

当前 `ApiDocumentCandidate` 在 `url` 后插入 `observed_url`，`UnifiedApiEndpoint` 在 `api_type` 后插入 `observed_url`。旧的合法位置参数调用会把 `type_hint/source` 或 `endpoint_id/path_template` 错映射到新字段；例如旧式 Endpoint 构造会得到错误的 URL 和 endpoint id。

当前 `ARL/app` 内部调用基本使用 keyword，因此暂未发现生产调用命中；但这是模型兼容面风险。建议将新字段追加到旧字段之后，或提供显式 keyword-only 构造入口，并增加旧位置参数兼容测试。

### R6-P2-02：范围语义注释与文档状态存在冲突

- [`api_candidate_registry.py:725-731`](../../ARL/app/services/api_candidate_registry.py:725) 的注释仍写“空集合放行”，实现已是空集合拒绝，应改为 fail-closed。
- 紧急修复文档顶部仍写“暂停第 9 批”而 §九末尾写“第 9 批可恢复开工”；同一文件还同时出现“T0-T6 全部完成”和“T5 进行中”。应统一为“第 9 批代码可在本 Review 通过后恢复；默认开关仍禁止”，避免后续 Agent 按旧结论执行。
- 当前 §九的 P0 验收没有覆盖“桥接拒绝后不得写 legacy records”，修复后应补入证据清单。
