## 3. 建议（不阻断，登记后续）

1. **完成通知未含积压读数**：done_pending 的钉钉/站内完成通知仍按"已完成"发送，正文不含
   `pending_wih/pending_wih_overflow` 计数。数据在 task_finalization stage metrics 中，通知文案
   可后续读取补一行"存在待处理积压 N"。涉及消息模板变更，建议与计划 4 通知面回归合并处理。
2. **done_pending 阻断周期复用基线**（`wih_periodic_reuse` 只认裸 done，本轮有意设计并注释）：
   若某 schedule 连续多轮 done_pending，将每轮全量 WIH 扫描，成本上行。建议运维手册注明；
   如实际发生频率高，再设计"pending 优先消费 + 干净轮次做基线"的折中。
3. **residual_total 跨策略重复计数**：同一主机可同时显影在 `pending_directory` 与 `pending_wih`。
   已在代码注释澄清"分策略计数是事实源、total 仅表达是否存在积压"；UI 展示阶段建议只呈现
   分策略值。
4. **计划 6 第 3 批约束重申**：`ApiCandidateRegistry`/`ApiDocumentQueue` 接管 endpoint 时，
   必须替换 `pending_backlog|api|*` 的"下一轮显影"为任务内消费并迁移旧键语义；js/path/site
   候选在本轮仍是 `open_other_candidates` 观测，不得被第 3 批宣称为已覆盖。

## 4. 已知限制（非缺陷）

1. `pending_*` 账本按策略各截断至 `TASK_FINALIZER_PENDING_MAX`：极端积压下账本条目可能少于
   计数；截断量可由"计数 − pending_recorded"推出。
2. `drain_rounds=0` 且队列有残余时决策为 done_pending：语义正确，但首次升级后周期任务
   终态字段的分布会变化，需纳入双架构 smoke 断言。
3. 前端 `docker/frontend` dist 未重建：旧 bundle 的 `normalizeTaskStatus` 按 "done" 子串规则
   已能把 done_* 归类为完成，不产生错误状态，但缺少专门的家族展示优化。
4. `test_task_orchestrator`/`test_web_site_fetch_orchestrator` 本机因缺 `xing` 无法导入
   （与既有基线一致）：本轮以依赖桩直接驱动真实编排器代码完成三终态映射与顺序验证，
   属补充证据，不能替代容器套件。
