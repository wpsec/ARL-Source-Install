# 02 计划2：核心架构解耦与分层重构

## 目标

在完成仓库收缩后，推进核心单体解耦，降低路由、任务编排、配置中心和导出链路的复杂度。

本计划采用 Rust + Python 混合架构：Python 保留业务编排和外部依赖，Rust 只承载经过基准确认的 CPU 密集型批处理。

本轮新增的主线是跨工具发现上下文治理：先统一响应、候选、来源和请求策略，再继续扩大单个 stage 的服务化拆分。全 Rust WIH 重写暂停，避免在数据流未打通前重复建设第二套扫描系统。

## 扫描速度与准确性治理（现行实施顺序）

在继续拆分 repository、orchestrator 和路由前，先按以下顺序处理扫描慢、结果不可见和失败不可追踪问题：

1. 建立 40 个目标的统一阶段指标基线，记录墙钟、CPU、网络等待、内存、输入输出、排队和失败结果。
2. 收敛 provider 网络可靠性：全局 IP/证书/域名去重，独立连接/读取超时、有限重试、受控并发、阶段预算、熔断和脱敏日志。
3. 将一次性域名任务改为同一 Task ID 下的渐进式发现队列和深度队列；发现结果先落库，队列清空后才标记 `done`。
4. 重构端口扫描批次：用户端口选择保持不变，`all` 最终必须覆盖 `0-65535`；批次最多 4 路受控并发，批次失败单独重试和标记，Nmap 进程有独立超时。具备 `CAP_NET_RAW` 时优先使用 `-sS`，仅在确认 raw socket 权限错误时按批次回退 `-sT`，并记录扫描类型、回退原因和次数。
5. 将文件泄漏候选保留为完整集合，按高价值路径优先、站点公平和全局受控并发执行；404 校准、超时、待处理和失败数量独立记录。
6. 将 WIH 拆为发现、提取、候选筛选和 URL 探测的可恢复批次；严格周期复用只允许同 schedule、目标和站点签名且不超过 24 小时，新增候选进入有界队列。
7. 收敛 Nuclei：启动或构建时预校验模板，`-as` 失败只允许一次带原因的 tags fallback，相同目标/profile 不重复执行。（已完成 2026-09-03：`_preflight_templates` 只读结构校验进 metrics；`-as`→tags 单次带原因回退既有；批次签名 `(targets,tags,auto_scan,模板目录)` 成功后去重，`duplicate_batch_skipped` 计数，失败批次不记账可重试。）
8. 扩大 Rust URL/JS/HTML 纯数据热点，保持批量 adapter，Rust 不访问外部服务。
9. 接入 Python fallback、每批 metrics 和阶段指标；Rust 导入失败、单批异常或结果校验失败只影响当前批次。
10. 上述运行时行为稳定后，再继续 repository、orchestrator、stage executor、配置中心和导出链路解耦。

### 运行语义冻结

- 没有总任务硬上限，但每个阶段、provider、批次和目标必须有预算。
- `test/top100/top1000/custom` 不得被改写；`all` 必须最终完成 `0-65535`，首批展示与最终 `done` 分离。
- CDN IP 默认不进入端口扫描队列，保留 CDN IP 与域名资产关系；站点发现对业务域名单独生成 80/443 HTTP 候选，不将未验证的 CDN 边缘端口写入 `IPInfo`。疑似全开放设备保留端口集合并跳过逐端口 `-sV` 放大，不能直接丢弃原始结果。
- `FindSite` 只可将端口阶段已确认的公网域名作为 DNS 视图漂移的受限例外；站点探测必须记录候选、DNS 跳过、例外放行、请求和失败数量，不能把误拦截表现为空结果。
- provider、端口批次、文件泄漏、WIH、Nuclei 的失败不能静默转为空结果。
- 阶段输入、输出、去重、过滤、排队、成功、超时、重试、失败、降级和来源关系必须可复算。

## 统一发现上下文与跨工具协同（新增主线）

### 目标

- 同一任务内同一请求 profile 的页面只获取一次，响应可以被爬虫、URLFinder、WIH、站点识别和 URL 探测共同消费。
- 爬虫、URLFinder、WIH、目录扫描和服务类型任务之间通过候选资产图联通，不再依赖某个工具的私有内存结果。
- 目录扫描的暴力流量与正常爬虫/WIH 流量隔离，避免局部 WAF 触发造成全站点连坐。
- 新子域、新 API、新页面和新目录候选自动按类型分发到后续策略，保留完整来源。

### 任务级上下文

新增 `DiscoveryContext`，只在当前 Task ID 内共享热数据，并通过持久化账本保存恢复所需状态：

- `ResponseRegistry`：保存规范化 URL、请求 profile、响应状态、类型、hash、有限正文和来源。
- `CandidateRegistry`：保存候选、候选类型、来源集合、父目标、深度、优先级和处理状态。
- `DiscoveryLedger`：保存幂等键、批次状态、失败/降级原因和待处理数量，供 worker 重启恢复。
- `RequestScheduler`：按 `normal/crawler/wih/directory/browser` 流量类别执行连接池、并发、超时、重试和预算控制。
- `SourceAggregator`：只合并结果，不删除来源；同一候选必须保留 `sources` 集合。

响应缓存键固定为：

```text
task_id + normalized_url + method + request_profile
```

幂等键固定为：

```text
task_id + stage + target + scan_profile + input_signature
```

### 事件分发

统一事件至少包括：

```text
PageFetched
UrlCandidateDiscovered
NewHostDiscovered
DirectoryCandidateDiscovered
EndpointCandidateDiscovered
WafSignalDetected
```

新子域事件必须经过 DNS/WAF 和范围校验后，同时进入站点、WIH、URLFinder 和目录扫描的相应队列；URLFinder 发现的新 API 必须进入 WIH URL 探测队列。

### 策略边界

- `SiteFetchStrategy` 只负责种子站点和基础响应。
- `CrawlStrategy` 负责递归页面覆盖。
- `UrlFinderStrategy` 只负责内容解析和候选生成，不再独立重复抓取页面。
- `WihStrategy` 消费响应和候选，负责接口、敏感内容和 URL 探测。
- `DirectoryScanStrategy` 保持字典探测完整性，但复用已完成响应并使用独立 WAF 隔离策略。
- `UrlProbeStrategy` 只处理尚未完成且符合范围和 profile 的候选。

### 实施顺序

截至 2026-09-03：第 1–5 步已完成首批接线（观测快照进任务收尾日志；`fetch_site`、爬虫、站点 URL 探测、URLFinder、page_intel、js_intel、WIH 记录和目录扫描已共享响应/候选/事件；调度为准入控制 + 有界等待 fail-open，未含真实连接池）。第 6 步 Rust 接入仍按“后置加速”原则等待数据流稳定后执行。

1. 统一观测请求数量、缓存命中、重复请求、候选传播和 WAF 类别状态。
2. 实现 Python `DiscoveryContext`，先接入 `fetch_site`、爬虫和站点识别，不改变对外结果。
3. 接入统一 HTTP 调度和响应复用。
4. 接入候选资产图和跨策略事件分发。
5. 让 URLFinder、WIH 和目录扫描消费共享上下文。
6. 最后把 Rust 接入统一内容处理层，并执行结果集合门禁。

## 重构前置：任务执行性能与统计修复

该阶段是进入本计划后续结构重构的 P0 前置门禁。当前任务样本中，64 个目标的总耗时为 9 小时 45 分 20 秒，其中 `wih_primary_scan` 占 8 小时 17 分 18 秒，约占总时长的 85%；`wih_urlfinder_sensitive` 又运行到 29 分 59 秒，接近 30 分钟阶段预算。此时直接拆分 `commonTask` 或重写 orchestrator，会把运行时问题带入新结构，无法判断性能变化来自架构还是调度行为。

具体的 WIH 复用、runtime 分级、URLFinder 止损和配置参数沿用 [WIH 提速与调度优化实施计划](./WIH提速与调度优化实施计划.md)；本节只定义进入核心架构重构前必须完成的修复门禁和回归要求。

### 修复目标

- `fast_mode=True` 必须真正受到轻量预算和升级条件约束，不能出现周期任务仍执行小时级主扫描。
- 每个 WIH 阶段必须有明确的总预算、结束原因和结果状态，超时不能伪装成正常完成。
- WAF 跳过必须作用于实际耗时链路，统计必须反映真实执行时间，并区分主机、站点和请求口径。
- 阶段父子耗时可以汇总展示，但累计耗时不能重复计算，且 UI 必须明确标识“汇总阶段”和“实际执行阶段”。
- 修复后形成可重复的性能基线，再开始路由、任务编排和 stage executor 拆分。

### 修复范围

#### 1. WIH 主扫描预算与调度

- 核对线上实际生效的 `WIH_LIGHT_TIMEOUT_SEC`、`WIH_MINIMAL_TIMEOUT_SEC`、`WIH_TIMEOUT_SEC`、`WIH_MAX_BATCH_SIZE`、`WIH_CONCURRENCY` 和 `WIH_CONCURRENCY_PER_SITE`，启动任务时记录最终生效值。
- 检查周期任务的 `fast_mode` 是否只停留在参数层，确保主扫描按 `light -> full` 的强信号升级，不因默认路径或回退逻辑重新进入全量深扫。
- 为一次任务设置 WIH 总预算；`minimal` 回退、重试和升级必须共享预算，禁止通过多个子阶段叠加出小时级长尾。
- 对每个 batch 记录 `reused`、`light`、`full`、`minimal`、`timeout`、`salvage` 和 `primary_escalated` 数量，区分“结果复用”“正常完成”和“超时保留结果”。

#### 2. URLFinder 敏感扫描止损

- 保留 `urlfinder_sensitive` 的发现能力，但把阶段总预算、连续无新增批次止损和候选优先级作为硬约束。
- 阶段触达预算上限时必须记录 `timeout` 结束原因、已处理候选数和已产生结果数，不能仅在 UI 中显示一个接近整值的耗时。
- 将慢候选、重复候选和低价值候选纳入单独计数，便于判断是候选规模、网络等待还是规则处理造成长尾。

#### 3. WAF 跳过链路与统计

- 明确 WAF 检测在 `wih_primary_scan`、endpoint probe、URLFinder 等阶段的生效边界；如果主扫描不接入 WAF，必须在阶段说明中明确标注，不能让汇总信息造成“主扫描已跳过”的误解。
- `WAF智能跳过` 不得使用固定 `0s` 作为执行耗时；应区分“检测耗时”“跳过节省量”和“无独立执行阶段”。
- 统一统计 `host/site/request` 三种口径，UI 展示时标明单位，避免与任务资产统计中的站点数、域名数混淆。

#### 4. 任务统计与可观测性

- 每个阶段统一记录 `started_at`、`finished_at`、`elapsed`、`status`、`end_reason`、输入数量、输出数量和关键预算。
- 父阶段只作为汇总视图，不参与子阶段累计；接口和前端统一使用同一套去重规则。
- 对 `<1秒`、`0秒`、阶段预算顶满等特殊值保留原始状态，不能只格式化成耗时文本后丢失诊断信息。

### 实施顺序

1. 先补充线上生效配置和阶段结束原因日志，确认本次 8 小时长尾是配置未生效、全量升级、回退叠加还是网络等待。
2. 修复 `fast_mode`、WIH 总预算和 batch 级超时/回退边界，确保周期任务可在预算内收敛。
3. 修复 `urlfinder_sensitive` 的预算顶满状态和无新增止损，并补充候选规模与结果增量指标。
4. 收口 WAF 实际接入边界和耗时统计，修复固定 `0s` 展示。
5. 完成一轮 64 目标代表性周期任务回归，保存阶段耗时、超时、复用、升级和结果量基线。

### 前置阶段验收

- 代表性周期任务中，`fast_mode=True` 的主扫描不会无条件进入完整深扫；每次升级都有可追溯原因。
- WIH 主扫描、回退、重试和 `urlfinder_sensitive` 均受显式预算约束，超时状态可在任务详情和日志中定位。
- 不再出现 `WAF智能跳过` 固定显示 `0秒` 且无法说明是否影响主扫描的情况。
- 父阶段汇总耗时与子阶段累计耗时不重复，任务总时长可以由阶段明细复算。
- 同一批代表性目标连续执行两轮后，能够区分复用、变化重扫和超时保留结果；性能和结果量基线已记录。
- 未满足以上条件前，不进入本文件后续的路由层、扫描编排和导出链路重构。

## Rust 热点迁移与 Python 边界

### Rust 热点迁移顺序

1. 采集 64 个代表性目标任务的 CPU 时间、网络等待、内存、阶段耗时、输入规模和结果数量。
2. 以 `urlfinder_extract.py`、`urlfinder_sensitive_scan.py`、`url_candidate_filter.py` 和 `web_info_intel_utils.py` 为第一批候选。
3. 先抽取批量接口和 Python adapter，再实现 Rust；禁止在没有等价 Python 基线的情况下直接替换。
4. Rust 接入稳定后，才继续路由、repository、orchestrator 和 stage executor 拆分。

### Rust 第一批职责

- 批量 URL/JS/HTML 文本提取。
- URL 归一化、相对路径和协议相对 URL 处理。
- 目标 host 范围过滤、模板路由和静态资源过滤。
- 记录去重、稳定 hash、候选排序和敏感目标筛选。

### Python 保留职责

- HTTP 请求、DNS/WAF 策略和网络超时。
- Celery 编排、阶段预算、重试、任务状态和统计。
- Mongo/Redis 读写、`WihRecord` 创建和结果持久化。
- Playwright、AI、`nuclei / afrog / NPoC` 外部程序调用。
- 现有 Go 版 `tools/wih` 的执行和结果协议。

### 内部接口与 fallback

- 新增独立 `ARL/native/arl_accel` PyO3/maturin crate。
- Rust 对外提供批量处理接口：输入页面文本、站点范围、已有记录和扫描选项；输出规范化记录和候选目标。
- Python 现有 `run_urlfinder_extract`、`run_urlfinder_sensitive_scan` 等公共函数签名不变，只在内部调用 adapter。
- Rust 输入无效时返回可识别的参数错误；运行异常返回运行时错误。adapter 必须记录阶段、批次和错误原因。
- `RUST_ACCEL_ENABLE=true` 时优先使用 Rust；加载失败或单批异常且 `RUST_ACCEL_FALLBACK_ENABLE=true` 时，仅对当前批次回退 Python 实现。
- 禁止静默回退；日志和指标至少记录 `backend`、`fallback_reason`、`batch_size`、`elapsed` 和 `fallback_count`。

### 明确暂不 Rust 化

- Mongo、Redis、任务状态和配置读取。
- Celery 编排、阶段预算和重试。
- Playwright、HTTP 网络 IO、DNS/WAF 判断。
- `nuclei / afrog / NPoC` 外部程序调用。
- 现有 Go WIH 全量重写。

## Rust 构建与运行时配置

- 生产镜像同时构建 amd64 和 arm64 release wheel，并在镜像构建阶段验证 `import arl_accel`。
- 主生产 Python 运行时统一按 Python 3.10+ 规划；旧 `ARL/docker/ARMWorker/Dockerfile` 的 Python 3.8 不纳入本轮验收。
- 固定 Rust、PyO3、maturin 版本和 `Cargo.lock`，构建时固定 glibc 兼容下限。
- `RUST_ACCEL_ENABLE` 控制是否启用 Rust 加速，默认开启。
- `RUST_ACCEL_FALLBACK_ENABLE` 控制 Rust 不可用或单批失败时是否回退 Python，默认开启。
- Rust 构建失败必须阻止生产镜像发布；运行时 fallback 只用于保证任务功能连续性，并必须可观测。

## 性能与一致性门禁

- Rust 候选热点的 p95 CPU 时间至少降低 30%，或吞吐达到 Python 基线的 1.5 倍；未达到时不纳入生产路径。
- 接入 Rust 后，端到端阶段耗时不得较基线恶化超过 5%；CPU 仅占阶段耗时小部分时，不强行迁移。
- Rust 与 Python 的规范化记录集合必须一致，不得减少有效结果；排序差异不能影响结果入库和 UI 语义。
- 使用 64 个代表性目标执行冷启动和热缓存两轮，分别记录 CPU、网络等待、内存、阶段耗时、fallback 次数和结果数量。

## 路由层收口

- 路由层不再直接拼 Mongo 查询和写库。
- 增加 repository / query service 层。
- 第一批优先从 `task / site / domain / api_console / export` 五块拆分。
- `ARLResource` 仅保留请求解析、响应序列化、通用分页协议，不再承载复杂业务查询规则。

## 扫描编排解耦

- `DomainTask`、`IPTask` 改为 orchestrator。
- 域名爆破、DNS、端口扫描、证书、站点抓取、WIH、PoC 扫描拆成独立 stage executor。
- `CommonTask` 收缩为生命周期、统计、任务收尾和 scope 校验。

## 配置与启动收口

- 移除业务启动副作用，不再依赖 Web 进程导入即执行初始化修复。（已完成 2026-09-03：`arl_update` 收口为 `app.tools.arl_bootstrap` 显式入口，由 `start_web.sh` 在 gunicorn 前调用；`import app.main` 不再要求 Mongo 可达。）
- `arl_update` 改成显式 bootstrap / migration 入口。
- `api_console` 从巨型单文件按配置域拆分：
  - 扫描配置
  - AI 去噪配置
  - 第三方集成配置
  - 运行态只读信息

## 导出链路重构

- 大导出统一走异步 job。
- 同步导出只保留小数据量和立即返回场景。
