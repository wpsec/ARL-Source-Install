# ARL 全系统自动化测试体系建设计划

状态：**已完成**（2026-10-19）。189 个 API 操作的路由与认证响应合同、显式公开接口、重点业务 API 合同、隔离依赖故障恢复、全栈任务 UI 和离线测试入口均已验收。真实扫描和真实 provider 在线调用按约定由用户手动验收，不属于自动化测试门槛。

## 摘要

为 ARL 建立可重复、可分批实施的全链路测试体系，覆盖 Flask API、Python 服务、Celery 任务、MongoDB/Redis/RabbitMQ、React 前端和 Docker Compose 运行环境。测试优先复用仓库已有的 `unittest`、Vitest、Playwright、Rust 测试、测试卫生检查和容器回归工具，不新增测试框架依赖。

当前盘点识别到 194 个 Python 测试模块、30 个前端 Vitest/Playwright 测试文件、39 个已注册 Flask Namespace、189 个 HTTP 操作和 37 个可见业务页面。最终完整离线运行的 Python 卫生统计为 1310 项、0 失败、0 错误、57 跳过；194 个模块均干净加载。9 项隔离系统测试通过，覆盖 RabbitMQ 发布失败恢复、重复投递幂等、MongoDB 暂不可用与重试恢复、常规重试、worker 重启、任务取消、重试耗尽、状态写回及 Redis 隔离；另有 1 项真实隔离后端 Playwright E2E 通过。32 项专用高风险 API 合同测试和 4 项逐路由合同测试通过。Node 24.21.0 下 lint、29 个 Vitest 文件/186 项、production build 和 8 项 fixture Playwright 通过；Rust 1.85.1 下 21 项单测、Linux/amd64 离线构建、原生 smoke 和两个 Python/Rust corpus（5 项、4 项）严格顺序对照通过。完整 `run-offline-tests.sh` 退出码为 0。构建输出有大 chunk 提示。执行报告路径和范围见 [`docs/testing/README.md`](../testing/README.md)；机器生成的逐操作清单见 [`docs/testing/test-inventory.md`](../testing/test-inventory.md)。

## 范围与约束

- 覆盖 ARL 自有的后端路由和服务、异步任务编排、数据持久化、前端页面、Rust 加速模块，以及 Compose 运行时中的 API/worker/数据库/消息队列协作。
- 扫描器和外部 provider 的内部实现不属于本仓库测试范围；FOFA、AI、GitHub、钉钉、ICP 等外部服务默认以固定 fixture 或 mock 验证 ARL 适配层。
- `192.168.10.205` 是指定的测试执行节点和靶场宿主。测试使用独立 Compose 项目、MongoDB 测试库与临时 tmpfs、Redis 命名空间、RabbitMQ vhost 和临时测试账号，不连接生产数据或复用生产凭据。
- 自动化测试不启动 ARL 真实扫描器，不访问扫描目标或公网；任务链路使用确定性阶段和 stub 扫描结果。真实扫描由用户后续手工验收，不纳入本计划的自动化验收范围。
- 测试地址、账号和凭据通过专用测试配置在运行时注入，不硬编码到源码、测试 fixture 或命令行日志中。测试日志需脱敏。
- 不改变产品 API、数据结构、权限语义和扫描流程；不在本计划中加入性能基准或外部扫描器自身的验证。

## 分阶段实施

### 阶段一：清点覆盖面并建立基线

- 从 Flask 路由注册表生成 API 操作清单，从前端路由注册表生成页面/模块清单，并列出任务主流程、外部服务边界和持久化边界。
- 将现有 Python、前端、Rust 测试映射到清单；每个 API 操作和前端业务路由都要有对应测试或明确的排除理由。
- 在隔离测试环境运行现有套件，记录当前 commit、运行环境、通过/失败/跳过数量；按产品缺陷、环境依赖、外网依赖、收集失败和测试污染分类。
- 先修复测试卫生与可执行性问题；不得将收集失败、零用例运行或未归因失败标记为通过。

### 阶段二：建立隔离测试设施

- 为测试 Compose 栈配置独立项目名、数据库/队列隔离、测试账号和可清理的数据卷，保证不会访问或覆盖已有部署数据。
- 普通单测、API 测试和 UI fixture 测试默认不出公网；外部 provider 响应及扫描器命令使用确定性 mock。
- 建立只提供固定页面的 HTTP fixture 服务，用于隔离环境中的服务可达性和响应处理测试；自动化流程不得把它作为 ARL 扫描目标。
- 测试数据使用固定、可重复生成的样例；清理仅作用于测试库、测试队列和测试卷。

### 阶段三：补齐后端单元测试与 API 合同测试

- 使用现有 `unittest` 覆盖任务状态映射、阶段调度、进度计算、重试/超时、结果归档、配置校验、查询过滤、持久化转换和序列化等核心逻辑；外部依赖默认 mock。
- 使用 Flask 测试客户端验证每个已注册 API 操作的路由可用性、认证策略和响应契约。认证策略测试需区分公开接口和受保护接口。
- 对任务、用户权限、资产、风险、策略、计划任务、导出、ICP、配置、GitHub 和系统监控等高风险接口，覆盖有效请求、无效输入、缺少/无效认证、越权访问、分页筛选、数据写入读取、依赖异常和错误脱敏。
- 这里的“高风险”按接口能触发的权限变化或数据副作用划分：重点检查未认证/错误角色是否被拒绝、不同用户之间是否存在 IDOR、输入错误是否安全拒绝、成功写入能否正确读回，以及异常响应是否泄露敏感信息；这不意味着 189 个操作都要穷举相同组合。
- 通过隔离 Compose 栈另做真实 HTTP 冒烟，确认部署后的路由注册和认证中间件工作正常。

### 阶段四：验证异步任务及依赖协作

- 使用测试 RabbitMQ、Redis 和 MongoDB 验证任务投递、消费、确认、重试、重复消息、worker 重启、取消、失败恢复、进度/终态写回和结果查询。
- 异步测试使用确定性任务阶段和 stub 扫描结果，验证任务从投递、执行到持久化及终态查询的链路；测试不得触发真实扫描。
- 覆盖 broker/worker/存储短暂不可用、超时、重试耗尽和部分结果等失败路径，确认状态和错误信息不会被伪装为成功。
- 复用现有 Rust 单测、Python/Rust corpus 一致性测试和原生 smoke，检查加速模块与 Python 行为的一致性。

### 阶段五：扩展前端与全栈功能测试

- 使用 Vitest 覆盖业务组件、状态转换、API client、加载/空/错误状态和交互边界；使用 Playwright fixture 验证导航、登录返回、筛选/分页恢复、主题、任务详情和任务 ID 绑定。
- 为所有前端路由和业务模块建立基本渲染/关键操作检查；重点防止同名任务误用名称而非 task ID 打开详情。
- 另设少量 Playwright 全栈流程连接隔离后端，以确定性测试任务验证“创建 → 入队 → 执行 → 结果持久化 → API/UI 查看”，并覆盖取消或失败后的状态呈现；扫描器结果使用 stub。
- 所有自动化 UI 和全栈流程都不得触发真实扫描。用户后续手工执行真实扫描并单独确认结果，不作为本计划自动化验收项。

### 阶段六：固化命令入口和分层验收

- 新增 `scripts/run-offline-tests.sh`，统一运行 Python 单测与卫生检查、Rust 测试、前端类型检查/Vitest/构建，以及基于固定 fixture 的 Playwright 测试。
- 新增 `scripts/run-system-tests.sh`，在指定测试主机上启动隔离 Compose 栈，并运行 API/worker/消息队列/固定 HTTP fixture 集成测试；旧版会删除固定容器且可联网构建的 `run-container-regression.sh` 已改为安全兼容入口。
- 当前仓库未发现 ARL 自身 CI 配置，本计划暂不引入新的 CI 平台；保留可重复脚本供开发和常规自动化调用。隔离 Compose/靶场套件由指定主机手动或定时执行。
- 每次运行保存简明汇总与日志，记录 commit、环境、通过/失败/跳过数量和失败归因；禁止输出凭据。失败项未归因前不得登记为通过。

## 验收标准

- API 操作清单和前端业务路由清单全部闭环：每项有对应测试，或有经过说明的排除理由；关键工作流覆盖正常、权限、异常和恢复路径。
- 现有与新增测试均可在隔离环境重复运行；测试卫生检查没有污染、收集失败或零用例假绿。跳过项必须有原因并通过显式开关控制。
- 离线单测、API 合同测试和 fixture UI 测试不访问公网、不依赖真实 provider 凭据；外部网络测试默认关闭。
- Compose 全栈测试只使用独立数据资源、确定性测试任务和 stub 扫描结果，能验证 API、worker、RabbitMQ、Redis、MongoDB 及前端对任务终态的协作；自动化不发起真实扫描，真实扫描由用户后续手工验收。
- Python、前端和 Rust 的既有测试入口及新增分层入口均有文档说明，运行结果可追溯到 commit 和测试环境。
- 不设置全仓统一行覆盖率门槛；完成标准是覆盖清单闭环、关键链路通过、失败有归因且测试环境隔离有效。

### 验收结果

- 189 个 API 操作逐项与运行时路由表对齐。187 个受保护操作逐项断言无 Token 时返回统一 JSON 错误包络；公开接口使用显式 allowlist，仅含登录和登出，并分别验证错误登录与登出成功响应。
- 高风险业务域由 32 项 API 合同测试和现有模块测试覆盖任务/用户权限、资产、风险、策略、计划任务、导出、ICP、配置、GitHub 与系统监控；策略创建/删除、系统监控响应和口令/所有者边界有直接 Flask 客户端成功/失败断言。逐域映射及边界见 `docs/testing/test-inventory.md`。
- 37 个可见页面均有路由注册检查和 Playwright 基础渲染；关键页面、路由历史、登录返回、筛选恢复和 Task ID 绑定另有交互覆盖。
- 隔离栈的 9 项服务集成覆盖 RabbitMQ 消息投递、发布连接失败后的恢复、重复投递幂等写入、MongoDB 暂不可用时错误结果与恢复重试、worker 重启、任务取消、重试耗尽、终态写回及 Redis 隔离。
- 全栈测试只使用固定任务、固定 provider 响应与隔离服务，不访问公网、不调用真实扫描器。真实扫描由用户之后手动验收。
